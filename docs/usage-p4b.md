# P4b: the Single sign-on section and one second factor for conductor-idp

conductor's "Single sign-on" section manages
[conductor-idp](https://github.com/openbasalt/samba-conductor-idp) from the
browser: OpenID Connect clients and SAML service providers (with guided
presets and SAML metadata import), signing keys, the session and consent
settings, and the sign-in activity per application. conductor also serves
its second factor to conductor-idp, so users have one enrollment and one
policy for both, security keys and passkeys included.

## How it works

```
browser --HTTPS--> conductor (user conductor) --Unix socket--> conductor-idp (user conductor-idp)
                    session, roles, 2FA          SO_PEERCRED:      management API (idpapi)
                    previews, audit              conductor only

browser --HTTPS--> conductor-idp --Unix socket--> conductor (2FA socket)
                    sign-in, 2FA page          SO_PEERCRED:    TOTP, recovery codes, security keys,
                                               conductor-idp   conductor's role-based policy
```

- conductor never signs anything and never sees a signing key: it calls
  conductor-idp's local management API (package `idpapi` of
  conductor-idp) as the signed-in administrator. conductor-idp checks the
  peer of every connection (SO_PEERCRED, the conductor user only) and
  writes every change to its own hash-chained audit log with that
  administrator (`conductor:<user>@<address>`); conductor audits the same
  actions in its log (`sso.*`).
- Administrators only (`sso.read`, `sso.write`; auditors and helpdesk see
  nothing). Every change is shown on a preview page and asks for the
  password and a fresh second factor: registering or changing an
  application, a new client secret, enabling, disabling or removing an
  application (removal also needs the client_id or the application's name
  typed), a key rotation, the policy.
- A form is validated by conductor-idp before it is proposed: "Preview the
  claims" (OpenID Connect) and "Preview the assertion" (SAML) build what a
  real user would get, with the same rules as the registration, and say
  whether that user may sign in.
- Allowed groups are picked from the directory (search by name or
  description, with the administrator's own connection) and stored by SID.
- A confidential client's secret is generated by conductor-idp, returned
  once, shown once on a page that is not cached and gone on a second visit;
  conductor keeps it nowhere and never logs or audits it.
- SAML metadata can be pasted, uploaded or fetched by https URL (by
  conductor-idp, once): it only prefills the form. The SP's signing
  certificate from the metadata lets conductor-idp verify the SP's signed
  logout requests (single logout).
- No new script source in conductor: the section uses no JavaScript.

## The 2FA socket

- conductor listens on `/run/conductor/mfa.sock` (systemd
  `conductor-mfa.socket`, owned by conductor with the conductor-idp group,
  0660) and admits only the conductor-idp user.
- conductor-idp asks whether a user is enrolled and must use a second
  factor (it sends the user's group SIDs; conductor maps them to its roles
  exactly as at its own sign-in), verifies codes (TOTP is refused when a
  security key is mandatory, `webauthn.admin_required`) and runs security
  key assertions for its sign-in page. Wrong codes count against the same
  per-user limit as conductor's sign-in, and each verification is audited
  (`idp.mfa_verify`, `idp.mfa_key`).
- Security keys registered in conductor work at the IdP when the IdP's
  origin is one of conductor's WebAuthn origins: on another host name, give
  both a common parent domain as `webauthn.rp_id`; on the same host name
  (another port), add the IdP's origin to `webauthn.origins`.

## Enabling it

On conductor's host:

1. Install conductor-idp as its `docs/install.md` describes, with its
   management API (section 8: `[api] enabled = true`,
   `conductor-idp-api.socket`).
2. In `/etc/conductor/conductor.toml`:

   ```toml
   [idp]
   enabled = true
   socket = "/run/conductor-idp/api.sock"
   ```

3. For one second factor (optional): `mfa_socket = true` in `[idp]`, the
   drop-in and `conductor-mfa.socket` of `install.md` ("Operating"), and
   `mfa.backend = "conductor"` in `idp.toml` (conductor-idp's install.md,
   section 9).
4. Restart conductor. The section appears in the sidebar of administrators.

## Lab run

The suite `e2e/tests/20-sso.spec.ts` runs on the lab snapshot that has
conductor-idp on dc1 next to conductor (`https://dc1.lab.conductor.test:9444`,
management API and conductor's 2FA), with conductor-idp's example SAML SP
next to the browser; the OpenID Connect relying party is the browser
itself (its redirect URI is intercepted and the code exchanged by the
test). It covers:

- an OpenID Connect app from the "OpenID Connect" preset with an allowed
  group picked from the directory, a claims preview for a real user, the
  confirmation with re-authentication, the secret shown once (gone on a
  second visit);
- the consent note and the session lifetime set from the Policy page;
- a user who registers a passkey in conductor and signs in to that app
  through conductor-idp with it (the app requires a second factor), with
  the consent note shown, then the token exchange (`amr` contains `mfa`,
  the `groups` claim has the picked group);
- a SAML app imported from its metadata (with its single logout endpoint
  and signing certificate), an assertion preview, a sign-in through the
  IdP, and single logout started by the app: its signed HTTP-Redirect
  request ends the IdP session without a confirmation and the app gets the
  IdP's signed answer;
- an administrator signing in at the IdP with conductor's authenticator
  code;
- an OpenID Connect key rotation, the certificate download, the activity
  page (both applications listed) and the IdP's audit chain;
- helpdesk without the section.
